## About

I am a Master's student in Computer Science at the **University of Dayton**, graduating **December 2026**, and I spend most of my time on the part of software that only shows up under load: delivery guarantees, retries, failure recovery, and the infrastructure underneath them.

The thing I actually care about is **whether a claim survives contact with evidence.** So when I built a webhook delivery service, I did not stop at "it has at-least-once delivery" — I turned the deduplication guard off, SIGKILLed the workers mid-flight, and counted the duplicates. There were ten. I turned it back on and counted again. Then I extended the observation window and found the guard was *deferring* duplicates rather than eliminating them — and wrote that down too, in the repo, next to the number it weakens.

That is the habit I would bring to a team: numbers that trace to a script anyone can re-run, and caveats stated before someone else has to find them.

Right now that looks like a **Go** delivery service on self-hosted **Kubernetes** — Terraform, ArgoCD, Chaos Mesh, OpenTelemetry, no cloud account anywhere — and a **Python** multi-agent runtime where four Claude agents delegate to each other inside network-isolated sandboxes under hard budget ceilings.

> **Open to:** **DevOps Engineer** · **Cloud / AWS Engineer** · **Site Reliability / Platform Engineer** · **AI Engineer** — new-grad roles, US-based, available **January 2027**.

## Featured Projects

<details open>
<summary><b>🔁 webhook-relay</b> — a webhook delivery service in Go, load-tested and chaos-tested &nbsp;<code>Go</code> <code>Kubernetes</code> <code>Terraform</code></summary>

<br />

This is the component that sits between an application and its customers' HTTP endpoints and makes sure events actually arrive. When you `POST` an event it is written to PostgreSQL inside a single transaction and acknowledged only once it is durable — so a crash one millisecond later loses nothing. A separate relay process claims batches out of that outbox table using `FOR UPDATE SKIP LOCKED` and pipelines them into Valkey Streams, where a consumer group hands each delivery to a pool of worker goroutines. Each worker signs the payload with HMAC-SHA256, sends it, and on failure re-schedules with full-jitter exponential backoff; after six attempts the event lands in a dead letter queue you can inspect and replay. Three guards wrap every send — a Lua token bucket for per-endpoint rate limiting, a circuit breaker, and a Redis `SETNX` dedup key — and the whole thing runs on a local k3d cluster that Terraform provisions from nothing, with ArgoCD syncing the manifests, Chaos Mesh injecting the failures, and OpenTelemetry traces flowing through it. No cloud account is involved anywhere.

| | |
|:--|:--|
| **Stack** | Go 1.25 · PostgreSQL 16 · Valkey 8 Streams · Kubernetes (k3d) · Terraform · Helm · ArgoCD · Chaos Mesh · Prometheus · OpenTelemetry · k6 · Cosign + SBOM |
| **Key challenge solved** | Proving the at-least-once guarantee instead of asserting it. Disabling the dedup guard and SIGKILLing workers mid-delivery produced **10 duplicates across 400 events**; with the guard, **0 within a ~3-minute window**. The duplicate count turned out to equal `WORKER_CONCURRENCY` exactly — meaning the throughput knob *is* the correctness blast radius. A longer observation window later showed the guard **defers** duplicates against a 15-minute TTL rather than removing them, and that caveat is documented in the repo beside the claim. |
| **Also measured** | ~**875 events/sec** ingest and ~**870/sec** delivery on a single 8-core laptop. Found the bottleneck by elimination — ruling out pool size and worker concurrency, then showing nothing was CPU-saturated — and traced it to the outbox relay making O(n) round trips per batch. Pipelining the enqueue was **+5.4%** on its own (769 → 811/sec); reaching 870 needed concurrency and pool size raised alongside it. Laptop numbers, single node. |
| **Repo** | **[github.com/singha105/webhook-relay](https://github.com/singha105/webhook-relay)** — `make demo` runs the whole thing in ~5 minutes |

Worth a look inside: the [system design docs](https://github.com/singha105/webhook-relay/tree/main/system-design), the [chaos experiments](https://github.com/singha105/webhook-relay/tree/main/chaos), and two written [postmortems](https://github.com/singha105/webhook-relay/tree/main/docs) for things that actually broke.

<details>
<summary><b>🤖 agent-team</b> — a simulated software engineering team of AI agents &nbsp;<code>Python</code> <code>FastAPI</code> <code>Docker</code></summary>

<br />

Four Claude agents — backend, frontend, database and DevOps — sit at desks in a dark room you watch in the browser. You assign a task to one of them; when it needs something it does not own, it calls a teammate itself and builds on the answer. The interesting part is not the demo, it is the constraints. An agent is a **YAML file**, not a class: name, role, model, prompt, tool grants and budgets are all data, and `runtime.py` knows nothing about any specific agent — proven by shipping a second, differently-sized team that runs with no code change. Every limit (iterations, tokens, delegation hops, cycles, wall clock) belongs to the **whole delegation tree** rather than a single run, because a per-run counter lets each new child reset the budget and quietly means nothing; when a queued task has no live parent, the budget is rebuilt from the database. Tool calls execute in a disposable container with `--network=none`, a read-only root filesystem and dropped capabilities — the allow-list is defence in depth, not the boundary, since `python -c` escapes any allow-list in one command. Everything lands in SQLite, so any run replays from the database alone: every step, every tool argument, every delegated child, every cent.

| | |
|:--|:--|
| **Stack** | Python 3.11–3.13 · FastAPI · SQLite · WebSockets · Docker · React + TypeScript + Vite · Anthropic Claude API |
| **Key challenge solved** | Making a multi-agent system **bounded and reconstructable** rather than a scrolling transcript. Budgets are enforced per delegation *tree*, cycle detection refuses a target already in the chain (that agent is blocked waiting on this very call — asking it would deadlock), and a refusal returns to the agent as a **tool error it can route around**, not an exception that kills the run. |
| **Verified** | **353 backend + 68 frontend tests** green on Python 3.11/3.12/3.13. Sandbox isolation checked against a real Docker daemon — host filesystem unreachable, egress fails with `ENETUNREACH`, a 60s sleep killed at the 5s timeout with no container left behind. Most tests run with no API key at all; a contract suite drives the real Anthropic SDK over real HTTP against a local server speaking the Messages API wire format. |
| **Repo** | **[github.com/singha105/agent-team](https://github.com/singha105/agent-team)** — `npm run demo` replays a real recorded run with no API key and no backend |

The max-flow solver underneath is **Edmonds–Karp, written from scratch** rather than imported, which is the whole point of the project.
